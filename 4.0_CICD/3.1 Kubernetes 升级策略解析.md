# Kubernetes 升级策略解析

## 1 概述

Kubernetes 提供了多种部署升级策略，帮助我们在不中断服务的情况下更新应用程序。本教程将详细介绍 Kubernetes 的主要升级策略，并通过实际示例演示如何实现零停机时间的应用升级。

---

## 2 升级策略类型

### 2.1 RollingUpdate（滚动更新）

滚动更新是 Kubernetes 默认的升级策略，它会逐步替换旧版本的 Pod，确保在升级过程中始终有可用的服务实例。

**特点：**

- 零停机时间
- 渐进式更新
- 可以控制更新速度
- 支持回滚

**配置参数：**

- `maxSurge`: 在更新过程中可以创建的超出期望副本数的 Pod 数量
- `maxUnavailable`: 在更新过程中可以不可用的 Pod 数量

### 2.2 Recreate（重新创建）

重新创建策略会先删除所有旧版本的 Pod，然后创建新版本的 Pod。

**特点：**

- 简单直接
- 会有短暂的服务中断
- 适用于不支持多版本并存的应用

### 2.3 Blue-Green（蓝绿部署）

蓝绿部署是一种通过维护两个相同的生产环境来实现零停机部署的策略。在任何时候，只有一个环境（比如蓝色环境）处理生产流量，而另一个环境（绿色环境）用于部署和测试新版本。

**特点：**

- 真正的零停机时间
- 快速回滚能力
- 完整的环境隔离
- 需要双倍的资源
- 适合关键业务应用

**实现原理：**

1. **蓝色环境**：当前运行生产版本的环境
2. **绿色环境**：部署新版本的环境
3. **流量切换**：通过 Service 或 Ingress 进行流量切换
4. **验证回滚**：新版本验证通过后切换流量，出现问题可立即回滚

## 4 滚动升级部署实践

### 4.1 RollingUpdate 参数分析

在我们的示例中：

- `replicas: 5`: 期望运行 5 个 Pod 副本
- `maxSurge: 25%`: 最多可以额外创建 1.25 个 Pod（向上取整为 2 个）
- `maxUnavailable: 25%`: 最多可以有 1.25 个 Pod 不可用（向下取整为 1 个）

```text
│                                                             │
│ maxSurge: 25% → 2个额外Pod                                  │

│ │ 最大Pod数: 7个 (5 + 2)                                 │ │
│ └─────────────────────────────────────────────────────────┘ │
```


### 4.2 升级流程

1. **开始升级**: Kubernetes 开始创建新版本的 Pod
2. **逐步替换**: 新 Pod 启动后，旧 Pod 被逐步终止
3. **健康检查**: 确保新 Pod 通过健康检查后才继续下一批
4. **完成升级**: 所有旧 Pod 被新 Pod 替换

### 4.3 实际操作步骤

#### 4.3.1 构建镜像

```bash
# 构建 v1 版本
docker build -t python-server:v1 .

# 修改 python 代码，把 V1 改为 V2
# message = "V2:Hello world, I'm host: " + socket.gethostname()

# 修改代码后构建 v2 版本
docker build -t python-server:v2 .
```

#### 4.3.2 部署应用

```bash
# 部署初始版本
kubectl apply -f python-deployment.yaml

# 检查部署状态
kubectl get deployments
kubectl get pods
```

#### 4.3.3 执行升级

```bash
# 更新镜像版本
kubectl set image deployment/python python=python-server:v2

# 或者直接编辑 deployment
kubectl edit deployment python
```

#### 4.3.4 监控升级过程

```bash
# 查看升级状态
kubectl rollout status deployment/python

# 查看升级历史
kubectl rollout history deployment/python

# 实时监控 Pod 变化
kubectl get pods -w
```

#### 4.3.5 回滚操作

```bash
# 回滚到上一个版本
kubectl rollout undo deployment/python

# 回滚到指定版本
kubectl rollout undo deployment/python --to-revision=2
```

### 5.3 Blue-Green 部署操作步骤

#### 5.3.1 初始部署

```bash
# 1. 部署蓝色环境（当前生产版本）
kubectl apply -f blue-deployment.yaml

# 2. 部署 Service（指向蓝色环境）
kubectl apply -f blue-green-service.yaml

# 3. 验证蓝色环境运行正常
kubectl get pods -l version=blue
kubectl get svc python-bg-service
```

#### 5.3.2 部署新版本到绿色环境

```bash
# 1. 部署绿色环境（新版本）
kubectl apply -f green-deployment.yaml

# 2. 等待绿色环境就绪
kubectl rollout status deployment/python-green

# 3. 验证绿色环境
kubectl get pods -l version=green
```

#### 5.3.3 测试绿色环境

```bash
# 1. 创建临时 Service 测试绿色环境
kubectl expose deployment python-green --name=python-green-test --port=80 --target-port=8000

# 2. 端口转发测试
kubectl port-forward service/python-green-test 8080:80

# 3. 在另一个终端测试
curl http://localhost:8080

# 4. 测试完成后删除临时 Service
kubectl delete service python-green-test
```

#### 5.3.4 切换流量到绿色环境

```bash
# 方法1: 使用 kubectl patch 命令
kubectl patch service python-bg-service -p '{"spec":{"selector":{"version":"green"}}}'

# 方法2: 使用 kubectl edit 命令
kubectl edit service python-bg-service
# 修改 selector.version 从 "blue" 到 "green"

# 验证流量切换
kubectl describe service python-bg-service
```

#### 5.3.5 验证和清理

```bash
# 1. 验证新版本运行正常
kubectl port-forward service/python-bg-service 8080:80
curl http://localhost:8080

# 2. 监控一段时间确保稳定
kubectl get pods -w

# 3. 清理蓝色环境（可选，也可保留作为下次部署的目标环境）
# kubectl delete deployment python-blue
```

### 5.4 快速回滚

如果新版本出现问题，可以立即回滚：

```bash
# 立即切换回蓝色环境
kubectl patch service python-bg-service -p '{"spec":{"selector":{"version":"blue"}}}'

# 验证回滚成功
kubectl describe service python-bg-service
curl http://localhost:8080
```

### 5.5 Blue-Green vs RollingUpdate 对比

| 特性 | Blue-Green | RollingUpdate |
|------|------------|---------------|
| 停机时间 | 零停机 | 零停机 |
| 资源消耗 | 双倍资源 | 1.25-1.5倍资源 |
| 回滚速度 | 瞬间回滚 | 需要重新部署 |
| 风险控制 | 风险最低 | 中等风险 |
| 复杂度 | 中等复杂 | 简单 |
| 适用场景 | 关键业务 | 一般业务 |

## 7 常见问题与解决方案

### 7.1 升级卡住

**原因**: 新 Pod 无法通过健康检查
**解决**: 检查应用日志和健康检查配置

```bash
kubectl describe pod <pod-name>
kubectl logs <pod-name>
```

### 7.2 资源不足

**原因**: 集群资源不足以支持 maxSurge
**解决**: 调整 maxSurge 和 maxUnavailable 参数

### 7.3 镜像拉取失败

**原因**: 镜像不存在或网络问题
**解决**: 检查镜像标签和镜像仓库连接

## 8 总结

Kubernetes 的滚动更新策略为我们提供了强大的零停机升级能力。通过合理配置 `maxSurge` 和 `maxUnavailable` 参数，结合健康检查和资源限制，我们可以实现安全、可靠的应用升级。

关键要点：

1. 选择合适的升级策略
2. 配置健康检查确保服务可用性
3. 合理设置资源限制
4. 监控升级过程并准备回滚方案
5. 在生产环境中先进行小规模测试
