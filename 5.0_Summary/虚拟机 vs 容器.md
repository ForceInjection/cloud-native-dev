# 为什么同样使用2个vCPU的App在VM中比在容器中运行的快？

> [为什么同样使用 2 个 vCPU 的 App 在 VM 中比在容器中运行的快？](https://mp.weixin.qq.com/s/hqjx-PgHEkUEoOnRbdiXTA)

## 引言

随着 Kubernetes 和容器技术的兴起和流行，许多团队不仅直接开发和部署新应用到 Kubernetes，还需要将现有应用迁移到容器。这些遗留应用通常部署在裸机或虚拟机 (VM) 上。

容器强调"构建一次，到处运行"，允许开发和运维团队以更轻量级和系统化的方式管理应用程序。然而，我们经常观察到，将应用原样迁移到 Kubernetes 后，其性能可能达不到预期。

本文主要从CPU的角度探讨为什么将服务从VM迁移到Kubernetes（容器）后可能会遇到的问题以及这些问题如何导致性能下降。

## 背景对比：虚拟机 vs 容器的资源管理

### 虚拟机的资源分配模式

当我们在使用虚拟机部署服务时，通常会请求固定数量的系统资源，例如具有 4 个 vCPU 和 16 GB RAM 等规格的虚拟机。然后，用户可以连接到虚拟机安装并运行所需的应用程序。

在虚拟机环境中：

- 资源分配是静态的、独占的
- 不需要考虑复杂的资源配置问题
- 不会触发CPU限流等问题
- 性能表现相对稳定和可预期

### 容器的动态资源管理

然而，在 Kubernetes 世界中，容器化应用的部署更加动态。为了避免影响其他容器的运行和耗尽节点资源，在部署Pod时进行适当的配置resource.request和resource.limit至关重要。

当应用的资源使用量达到配置值时，系统将采取相应的限制操作：

- **CPU**：导致 CPU 节流（throttling）
- **内存**：触发 Out-Of-Memory Killer

如果应用开发人员没有正确配置resource.limit和考虑程序的运行逻辑，很容易触发CPU节流。这通常表现为 p95 或 p99 等百分位数的意外性能问题，或者随着创建更多线程而性能下降的情况。

## 深入理解：什么是CPU节流

### cgroup 与 Kubernetes 资源管理的关系

要理解 CPU 节流，掌握 cgroup 和 Kubernetes 的resources.request/limit之间的实际关系至关重要。

### CPU 请求（Request）的工作原理

在 Kubernetes 中，CPU 请求有两个主要用途：

1. **调度决策**：Kubernetes 会聚合 Pod 中所有容器的请求，使用该值来过滤没有足够资源进行调度的节点（从而得到可以调度的候选节点）
2. **CPU时间分配**：Linux 内核 CFS（完全公平调度程序）将 CPU 时间分配给目标容器（CPU shares）

#### 实际案例分析

让我们考虑部署一个具有三个容器的服务，每个容器的 CPU 请求分别为 250m、250m 和 300m：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: www-deployment-resource
spec:
  replicas: 1
  selector:
    matchLabels:
      app: www-resource
  template:
    metadata:
      labels:
        app: www-resource
    spec:
      containers:
        - name: www-server
          image: hwchiu/python-example
          resources:
            requests:
              cpu: "250m"
        - name: app
          image: hwchiu/netutils
          resources:
            requests:
              cpu: "250m"
        - name: app2
          image: hwchiu/netutils
          resources:
            requests:
              cpu: "300m"
```

#### CFS调度周期的实际运行

假设一致认为 1 个 vCPU 等于 1000ms，但CPU 操作并不是以 1 秒（1000ms）为单位发生的。CFS 运行期间，每次运行的时间由 cgroup 参数cfs_period_us决定，默认为 100ms。

在100ms间隔内，每个应用的请求时间为：

- 容器1：25ms
- 容器2：25ms  
- 容器3：30ms
- 剩余时间：20ms（由三个容器竞争获得）

**CPU调度时间分配图示：**

```text
                        CPU 调度时间轴 (100ms 调度周期)

┌─────────────────────┬─────────────────────┬─────────────────────┬─────────────────────┐
│         容器1        │         容器2        │         容器3       │      竞争时间段       │
│       (25ms)        │       (25ms)        │       (30ms)        │       (20ms)        │
├─────────────────────┼─────────────────────┼─────────────────────┼─────────────────────┤
│     保证CPU时间      │     保证CPU时间      │     保证CPU时间       │   三个容器竞争获得     │
│    🔒 独占执行        │    🔒 独占执行       │   🔒 独占执行         │   ⚡ 动态分配         │
└─────────────────────┴─────────────────────┴─────────────────────┴─────────────────────┘
 ↑                    ↑                    ↑                    ↑                    ↑
0ms                  25ms                 50ms                 80ms                100ms

说明：
• 🔒 保证时间：容器独占CPU资源，性能稳定
• ⚡ 竞争时间：多个容器竞争剩余CPU时间，可能产生性能波动
• 总配额：容器1(25%) + 容器2(25%) + 容器3(30%) = 80%，剩余20%用于竞争
```

CFS通过CPU份额的设置来保证应用能够在每个周期内使用请求的时间。这可以看作是 CPU 运行时间的下限。

#### cgroup v2 的实现

在使用 cgroup v2 的环境中，底层使用cpu.weight实现：

```bash
ubuntu@hwchiu:/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-podacdcc83d_4cca_4271_9145_7af6c44b1858.slice$ cat cri-containerd-*/cpu.weight
121010
ubuntu@hwchiu:/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-podacdcc83d_4cca_4271_9145_7af6c44b1858.slice$ cat cpu.weight
32
```

在上面的示例中，CPU 权重按比例计算为 25:25:30，即 10:10:12。总权重为32。

### CPU限制（Limit）的影响

Kubernetes 中的 CPU 限制被定义为 CPU 使用量的上限。当CPU使用量达到这个限制时，就会触发CPU节流，这是导致容器性能下降的主要原因。

**CPU节流机制图示：**

```text
正常运行状态 (无节流)
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│████████████████████████████████████████████████████████████████████████████████████████████████│
│                              应用正常使用CPU (< Limit)                                        │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘

触发节流状态 (CPU使用达到Limit)
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│████████████████████████████████████████████████████████████████████████████████████████████████│ <- CPU Limit
│████████████████████████████████████████████████████████████████████████████████████────────────│ <- 应用被节流
│████████████████████████████████████████████████████████████████████████████████████              │    (强制等待)
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
     运行时间                                                                    等待时间
```

**节流对性能的影响：**

- ⚠️ **延迟增加**：应用被强制暂停，等待下一个调度周期
- 📉 **吞吐量下降**：有效工作时间减少
- 🔄 **不可预测性**：性能表现变得不稳定

## 性能差异的根本原因

### 1. 资源隔离机制的差异

**虚拟机**：

- 硬件级别的资源隔离
- 独占式的CPU分配
- 没有复杂的调度限制

**容器**：

- 软件级别的资源隔离（cgroup）
- 共享式的CPU调度
- 受到request/limit配置的严格限制

### 2. CPU调度的复杂性

在容器环境中，CPU调度需要考虑：

- 多个容器之间的公平调度
- Request保证的最小资源
- Limit限制的最大资源
- CFS调度器的时间片分配

这种复杂的调度机制虽然提高了资源利用率，但也引入了额外的开销和潜在的性能瓶颈。

### 3. CPU节流的性能影响

当容器达到CPU limit时：

- 进程被强制暂停执行
- 等待下一个调度周期
- 导致延迟增加和吞吐量下降
- 特别影响CPU密集型应用的性能

## 优化建议

### 1. 合理配置资源限制

```yaml
resources:
  requests:
    cpu: "500m"    # 保证最小资源
    memory: "512Mi"
  limits:
    cpu: "1000m"   # 避免过度限制
    memory: "1Gi"
```

### 2. 监控CPU节流指标

定期检查以下指标：

- `container_cpu_cfs_throttled_seconds_total`
- `container_cpu_cfs_periods_total`
- CPU利用率和节流比例

### 3. 应用层面的优化

- 优化应用的CPU使用模式
- 减少不必要的CPU密集型操作
- 考虑异步处理和批量操作

### 4. 集群层面的调优

- 合理规划节点资源
- 避免资源超分配
- 使用节点亲和性和反亲和性

## 结论

虽然容器技术带来了诸多优势，但在CPU性能方面确实存在一些挑战。理解虚拟机和容器在资源管理上的根本差异，以及CPU节流机制的工作原理，对于成功迁移和优化容器化应用至关重要。

通过合理的资源配置、持续的性能监控和针对性的优化，我们可以最大程度地减少这些性能差异，充分发挥容器技术的优势。
